How Doqua works

A short tour of the pieces, so that the rest of the documentation makes sense.

Windows and the event loop

Application.Run shows the main Window and processes events (mouse, keyboard, focus, resizing, timers) until that window is closed. All windows and controls belong to the thread that runs it; call them from there only. Timer callbacks and event handlers all run on that thread, one at a time.

The control tree

A window shows one Window.Content control that always fills it. Containers such as Panel, TabControl and SplitContainer hold further controls; every control has a Control.Parent, a position relative to it (Control.X, Control.Y) and a size. The last child is drawn on top and receives the mouse first.

Controls are drawn by the framework: for each control it calls Control.OnRender with a DrawingContext whose origin is the control's top-left corner and whose clip is the control's bounds, then draws its children on top. See Custom drawing.

Rendering

Doqua renders in software into a 32-bit pixel buffer and copies it to the window (SetDIBitsToDevice on Windows, XPutImage on X11). Changes do not redraw immediately: Control.Invalidate (called by every property setter) schedules one redraw, so many changes in one event handler produce a single frame.

Text is drawn with the operating system's font engine (GDI on Windows, FreeType with fontconfig on Linux); PNG files are decoded and encoded by Doqua itself.

Events

Doqua uses ordinary .NET events: button.Click += (sender, e) => .... Every event has a protected virtual OnXxx method that raises it, so a subclass can override the method instead of subscribing. Keyboard and mouse wheel events travel from the focused (or hovered) control up through its parents until one sets Handled. See Input.

Platforms

A small internal interface separates the controls from the operating system; there is one implementation for Win32 and one for X11 (Platform notes). Everything above it — controls, layout, drawing, text layout — is shared.
